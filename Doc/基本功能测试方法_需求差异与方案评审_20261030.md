## 一、评审结论（先看这里）

### 1.1 一句话结论

当前固件已具备"自动充电 + 旁路/逆变输出 + 三路温度保护 + 过载停机 + 串口屏显示"的完整主干，
但**与本次工作簿的需求存在系统性偏差**，偏差集中在四类：

1. **时间常数差一个量级**：空载自停 `60s` vs 需求 `30min`；按键长按 `500ms` vs 需求 `2s`。
2. **缺"模式"语义**：需求要求"短按/长按"承载"自动关 vs 常开"两种输出模式，固件只有单一 toggle。
3. **缺"分级"语义**：需求是"500W 告警 / 700W 停机 / 55→60℃ 分级 / SOC 双色"，固件是"1100W 一刀切 / 55℃ 锁死"。
4. **UI 能力边界**：DWIN 驱动只实现 `0x82 写 VP`，**颜色、字体、字号、对齐、图标闪烁全部做不到**，
   需求 #2/#3/#4/#5 有一半依赖**屏端 DGUS 工程改造 + 新增 VP**，不是纯固件需求。

`"--"` 在全工程**零命中**。

**差距**：需求的"未接负载 → `--`"这一分支根本不存在；且旁路工况被当成"不可见"处理。

**方案**：

1. 新增"负载在位"判据（放在 `app_display_task.c`，只读快照，不碰控制）：
   ```c
   #define TIME_LOAD_PRESENT_W  5      /* 负载在位阈值, W (与 1W 空载判据解耦) */
   bool load_present = (m != NULL) && m->out_ok && (m->vout_p_w >= TIME_LOAD_PRESENT_W);
   ```
2. `text_time_update()` 增加最高优先级分支：
   ```
   输出已开(OUT 或 UPS 图标亮) && !load_present  → 写 "--"
   输出已开 && load_present && 估计有效          → 现逻辑
   输出已开 && load_present && 估计无效          → 写 "--"（不再写 0 MIN）
   输出未开                                      → 写空（保持）
   ```
3. 旁路工况：`time_visible` 增加 `icon_ups` 条件，使"市电直通 + 空载"也能出 `--`
   （市电直通时无"剩余时间"概念，永久 `--` 也符合直觉）。
4. 顺手修 `else` 分支缺 `valid` guard 导致空闲态每 3s 重发 15B 空格的问题（省总线）。

**改动**：`app_display_task.c`（1 函数 + 2 常量）、`app_display_task.h`（可选新增 `VP_TEXT_TIME_EMPTY` 宏）。
**工作量**：0.5 人日（含屏上验证）。
**风险**：`--` 的**居中/对齐**由屏端控件决定，固件只补尾部空格；若屏端左对齐，
`--` 会贴左。需屏端把 TextTime 设为居中，或固件写 `"   --    "`（9 字符居中）——建议后者，零屏端改动。

### SW-3 过载分级：>500W 告警 / >700W 10min 停机（工作簿 #3）

**需求**：
1. 交流输出功率 >500W → **声光报警**（蜂鸣器 2.0s 周期叫；OVERLOAD 图标 2.0s 周期闪动）
2. 交流输出功率 >700W 持续 **10 分钟** → 关闭交流输出

**现状**：
- `output_overload_check()`（`app_main_task.c:1176-1198`）：`m->vout_p_w > 1100W`（原始值）持续 **5s** → 清 `ac_out_requested` + 2 声短鸣。
- 显示（`app_display_task.c:279-280`）：`m->online && vout_p_w > 1100W` → 文本 `OVERLOAD` 常亮；
  **注意判据不一致**：保护用 `m->out_ok`、显示用 `m->online`。
- 无声、无闪烁；报警灯只在"有 ERR 码"时 500ms 闪，过载不是 ERR 码 → **灯不亮**。

**⚠️ 硬冲突（必须先裁决 D1/D2）**：

| 项 | 现网 | 需求 | 冲突 |
| --- | --- | --- | --- |
| 额定功率 | 1000W | ? | 若 >700W 就关机，**1000W 额定无法成立** |
| 告警门限 | — | 500W | 500W 告警 + 700W 停机，跨度仅 200W |
| 停机门限 | 1100W | 700W | 1100W 是"短路/冲击兜底"，与 700W 分级是**不同语义** |

**三种可能的解读，需产品选一**：

- **解读 A（推荐）**：700W 是**新硬件的额定功率**（换逆变器/变压器），则 `BOARD_PWR_RATED_W` 改 700，
  500W = 额定×0.7 告警、700W = 额定×1.0 持续 10min 停机。现有 1100W 兜底改为 `700×1.1=770W/5s`。
- **解读 B**：500/700W 只针对**某一路输出**（如 DC/USB 口），与 AC 1000W 无关 → 需新增通道计量。
- **解读 C**：700W/10min 是"长时过载"，1100W/5s 保留为"冲击过载"，两级并存 →
  则需明确 700~1100W 区间：先 10min 停机，还是先 5s 停机？（5s 会先触发，10min 永不生效）

> **不裁决无法编码**：解读 C 下"10min 停机"是死逻辑。

**方案（以解读 A 为例）**：

1. `Board.h` 新增分级常量（与 `*_TMP_WARN/FAULT_TH` 同风格）：
   ```c
   #define BOARD_PWR_ALARM_W       500u    /* 声光告警门限 */
   #define BOARD_PWR_TRIP_W        700u    /* 停机门限 */
   #define BOARD_PWR_TRIP_HOLD_MS  600000u /* 10min 持续 */
   #define BOARD_PWR_SHOCK_W       770u    /* 冲击兜底 (原 1100) */
   #define BOARD_PWR_SHOCK_MS      5000u
   ```
2. 把 `output_overload_check()` 重构为 `output_power_supervise()`，输出三态：
   `PWR_OK / PWR_ALARM / PWR_TRIP`，分别驱动"显示节奏"和"继电器动作"：
   ```
   p > SHOCK_W 持续 SHOCK_MS   → TRIP（立即，沿用现逻辑）
   p > TRIP_W  持续 TRIP_HOLD  → TRIP
   p > TRIP_W                  → 累计计时（不清零，除功率回落）
   p > ALARM_W                 → ALARM（进入节奏器）
   ```
   **计时器设计注意**：10min 计时不能因瞬间掉载清零，建议用"滑动积分/漏桶"
   （每 20ms 累加 `dt`，功率回落时按 1/10 速率衰减），否则真实负载的周期性波动会让 10min 永不达成。
3. 声光由 6.1 节奏器统一驱动（period=2000ms）：OVERLOAD 图标亮/灭 + 蜂鸣 1 短鸣 + 红灯同相位。
4. 显示侧新增 `VP_ICON_OVERLOAD`（屏端变量图标）+ 保留 `VP_TEXT_ALARM` 文本（双保险，符合 image1 的
   "ERR88 & OVERLOAD" 同屏要求）。同时**统一判据**为 `m->out_ok`（修掉 `online/out_ok` 不一致）。

**改动**：`Board.h`、`app_main_task.c`（重构 1 函数 + 节奏器）、`app_display_task.c/.h`（新增图标 VP + 闪烁逻辑）。
**工作量**：2~3 人日（含 10min 长测）。
**风险**：
- 10min 长测需要可编程电子负载，**测试台架是前置条件**；
- 若 500W 告警用现有蜂鸣器 250ms 短鸣，2.0s 周期听感偏"稀疏"，建议改用 `drv_buzzer_long_sound(300)` + 1.7s 间隔。

### SW-4 温度分级：35℃ 联动 / 60℃ 停充停放（工作簿 #4）

**需求**：
1. 电池 NTC >35℃ → 风扇转；屏上 `Temp` 图标 **1.0s 周期闪动**；显示风扇图标
2. 电池 NTC >60℃ → 关闭电池充电和放电

**现状核对**：

| 子项 | 现状 | 结论 |
| --- | --- | --- |
| 35℃ 开风扇 | `fan_manage()` 主风扇 `bat>=350 \|\| chg>=350` 开、都 `<=300` 关 | ✅ **已实现**（迟滞 5℃） |
| Temp 图标 | `app_display_task.c:244-249`：任一路 `>=350` 或 OTP → 值 8，**500ms 静态重写** | ⚠️ 有图标但**常亮**，且**无迟滞**（34~35℃ 抖动） |
| 风扇图标 | **不存在**（`app_display_task.h:51-57` 只有 7 个图标 VP） | ❌ 需屏端 + 固件 |
| 60℃ 停充+停放 | 实为 **55℃** 且 `enter_fault()` **全局跳闸 + 不可恢复**（`fault_active` 无清除点） | ❌ 阈值不符、粒度不符、恢复策略不符 |
| 停充/停放分级 | `thermal_protect()` 单出口 `enter_fault()`，不支持"只停充"或"只停放" | ❌ 结构不支持 |

**方案**：

1. **阈值**：新增 `BOARD_PROT_BAT_TMP_DERATE_TH 600`（60℃）。
   `BAT_TMP_FAULT_TH`(550) 有两种处理：
   - 若产品确认 60℃ 才是故障点 → 把 550 改成 600，并**启用现有的 450(45℃) WARN 档**作为预警；
   - 若 55℃ 仍有保护意义 → 55℃ 视为"降载"，60℃ 才"停机"。
   **建议后者**（见 D9），保留安全余量。
2. **新增"降载"通道（不走 FAULT）**：
   ```c
   /* thermal_derate(): 在 thermal_protect 之前执行, 返回是否处于降载 */
   bool thermal_derate(const TEMP_INFO_T *t)
   {
       bool bat_hot  = (t && t->bat_temp >= BOARD_PROT_BAT_TMP_DERATE_TH);
       bool bat_ok   = (t && t->bat_temp <= BOARD_PROT_BAT_TMP_DERATE_TH - 50); /* 5℃ 滞回 */
       /* 60℃: 撤充电请求 + 撤输出请求, 不进 fault_active */
       if (bat_hot)  { s_state.flags.need_charge = false; s_state.flags.ac_out_requested = false; }
       return bat_hot;
   }
   ```
   回到 55℃ 以下：**充电自动恢复**（`charge_strategy_update` 会重算 `need_charge`）；
   **输出不自动恢复**（安全优先，等用户按键）—— 这一点需产品确认（D9）。
3. **Temp 图标 1.0s 闪烁**：固件在 `display_refresh()` 内用 `HAL_GetTick()` 相位翻转：
   ```c
   bool phase = ((HAL_GetTick() / 500u) & 1u) != 0u;   /* 0.5s 亮 / 0.5s 灭 = 1.0s 周期 */
   drv_dwin_set_value(VP_ICON_TEMP, (temp_alert && phase) ? ICON_TEMP_ON : ICON_OFF);
   ```
   注意当前刷新粒度 500ms，恰好可表达 1.0s 周期（每 2 帧翻一次），**无需改任务周期**。
   同时给图标加 5℃ 迟滞（35 亮 / 30 灭），与风扇一致，消除抖动。
4. **风扇图标**：屏端新增 `VP_ICON_FAN`（建议 `0x2010`），固件写 `drv_fan` 实际状态（`fan_main_on || fan_aux_on`），
   与 Temp 图标同相位（或常亮，需 UI 定）。

**改动**：`Board.h`、`app_main_task.c`（新增 `thermal_derate` + 主循环插入 1 行）、`app_display_task.c/.h`、屏端工程。
**工作量**：固件 1.5 人日 + 屏端 0.5 人日。
**风险**：
- "停放电"若走"撤输出请求"，则**旁路（市电直通）也会被切断** —— 需要明确"放电"是否含旁路。
  电池 60℃ 时旁路其实不经过电池，理想行为是**只切逆变**、保留旁路（旁路=市电直供，不发热）。
  **建议：60℃ 时 `ac_out_requested` 仅在 `mode==INVERT` 时撤销**，旁路保留。这是本方案对需求的合理化修正。
- `enter_fault` 不可恢复的问题在 #4 里必须绕开，否则用户每次过温都要断电重启。

**替代方案对比**：

| 方案 | 屏端改动 | 固件改动 | 风险 |

#define BOARD_SOC_COLOR_RED_PCT     10u    /* 红色门限 */

且**带 1%~2% 迟滞**，避免 20% 临界点颜色来回跳。

**同时要澄清的**（并入 D10）：
- `low_soc=10`（内部告警位）与红色 10% 是同一件事吗？若是，应把 `SYS_ALARM_LOW_SOC` 接进显示链路；
- `<10%` 时除了变色，是否要**禁止逆变**？（现 `INV_MIN_SOC_PCT=1`，形同虚设）

**工作量**：屏端 1 人日 + 固件 1 人日。

### SW-8 市电在位不需重按 AC / 掉电转逆变（工作簿 #8）

**需求**：接市电 220V，如果在交流输出的情况下，**不需要再按 AC 键输出，直接逆变输出**。

**现状（关键缺陷）**：

```c
/* app_main_task.c:1556-1561 —— AC 掉电守卫 */
if (s_state.mode == WORK_MODE_CHARGE_BYPASS && ac != AC_INPUT_PRESENT)
{
    input_abort();   /* → power_abort() → ac_out_requested = false; 全断; 3 声短鸣 */
    return;
}
```

即：**市电一掉 → 输出请求被清空 + 全部继电器断开 → 用户必须重新按 AC 键**。
`mode_decide()` 里"AC_ABSENT → WORK_MODE_INVERT"的分支**永远轮不到执行**（被守卫提前 return）。

同时 `AC_INPUT_UNKNOWN`（HLW8110 瞬间失步/换相抖动）也会触发同一路径 → **误掉输出**。

**方案（分两层，第一层必做，第二层看 D6）**：

**第 1 层：请求锁存与通路解耦（纯软件，1~2 人日）**

1. `power_abort()` 拆成两个函数：
   ```c
   static void route_all_off(void);              /* 只断继电器, 不动请求 */
   static void power_abort(void);                /* 断 + 清请求 (故障/关机用) */
   ```
2. AC 丢失守卫改为"**只停市电侧，保留输出请求**"：
   ```c
   if (s_state.mode == WORK_MODE_CHARGE_BYPASS && ac == AC_INPUT_ABSENT)
   {
       route_all_off();          /* 断 AC_CTRL/CHG_* */
       /* ac_out_requested 保持不变 */
       /* 不鸣 3 声, 只记日志; 让 mode_decide 下一拍切 INVERT */
   }
   ```
   `ac == AC_INPUT_UNKNOWN` 改为**保持现状 + 5s 超时兜底**（`PATH_INPUT_WAIT_MS` 已有 5000 常量可复用），
   避免瞬态抖动断输出。
3. `AC` 恢复（ABSENT → PRESENT）时，因为请求还在，`mode_decide` 自动切回旁路 → 输出**无按键恢复**。
   这正好满足需求 #8 的"不需要再按 AC 键"。

**第 2 层：切换时间（看 D6）**

现网逆变启动三段时序 = 预充 1.5s + 直连 0.5s + 输出 1.5s ≈ **3.5s**，且从 IDLE 起步。
若产品要求"UPS 级切换"（<20ms），必须改硬件/控制策略：

| 方案 | 做法 | 切换时间 | 代价 |
| --- | --- | --- | --- |
| ① 现状 + 请求锁存 | 掉电后重新走三段启动 | ≈3.5s | 纯软件；输出会断 3.5s |
| ② 逆变热备 | 有市电时保持 PD4/PD7 吸合、逆变器空载运行，掉电只切 `AC_CTRL→INV_OUT` | ≈继电器吸合 **10~20ms** | 待机损耗↑、需硬件确认逆变器支持长期空载 |
| ③ 双转换（在线式） | 一直走逆变，市电只充电 | 0ms | 效率↓、发热↑，不适合本产品 |

> **建议**：先实施第 1 层（收益明确、风险低），切换时间作为 **#9 的硬件指标**单独定义；
> 若选 ②，需硬件确认"逆变器能否长期空载待机"与"AC_CTRL 与 INV_OUT 是否允许机械并联风险"。

**风险**：
- 第 1 层改完后，"掉 AC 不再鸣 3 声"会改变现场验收习惯，需同步更新测试判据；
- 如果不做第 2 层却承诺 UPS 切换，**验收必然不通过** —— 这是最容易埋雷的一条。

### SW-10 0.5h 无负载自动关交流输出（工作簿 #10）

**需求**：如果 0.5 小时内电源没有通过交流输出接口给设备供电，电源将自动关闭交流输出。

> 功能测试表进一步细化：**短按 AC 开输出 → 30min 未带载自动关**（指示灯慢闪呼吸）；
> **长按 AC 开输出 → 常亮，永不自动关**（适合冰箱这类间断负载）。

**现状**：
- `output_idle_check()`（`app_main_task.c:1120-1152`）：**仅 `INVERT_STATE_RUNNING`**，
  `vout_p_w < 1W` 持续 **60s** → 清请求 + 2 声短鸣。
- **旁路（`BYPASS_STATE_RUNNING`）完全没有空载检测**。
- ACOUT 长按事件（`KEY_LONG_VALUE_ACOUT`）在 `app_main_task.c:1216` 被 `default:` 丢弃。
- 无 AC 专用指示灯（`work_led_process()` 绿灯 1s 闪是固定心跳，与输出无关）。

**方案**：

1. **新增输出模式状态**（与现有 `flags` 并列）：
   ```c
   typedef enum { AC_OUT_MODE_OFF, AC_OUT_MODE_AUTO, AC_OUT_MODE_LATCH } ac_out_mode_t;
   /* AUTO: 短按进入, 30min 空载自动关; LATCH: 长按进入, 不自动关 */
   ```
2. **按键语义**：
   | 键 | 事件 | 动作 |
   | --- | --- | --- |
   | ACOUT | 短按 | OFF → AUTO；AUTO/LATCH → OFF |
   | ACOUT | 长按（800ms） | OFF → **LATCH**；LATCH → OFF |
   | ONOFF | 短按 | 显示屏开/关（SW-1 配套，见下） |
   | ONOFF | 长按（改 2s） | 关机 |

3. **空载计时统一**：把 `output_idle_check()` 扩展为"旁路 + 逆变"统一判据：
   ```c
   bool out_running = (BYPASS_STATE_RUNNING || INVERT_STATE_RUNNING);
   bool no_load     = out_running && m->out_ok && (m->vout_p_w < AC_IDLE_PWR_W);
   /* AUTO 模式 && no_load 持续 AC_IDLE_STOP_MS(1800000) → 关输出 + 1 短鸣 */
   /* LATCH 模式 → 不计时 */
   ```
   阈值建议从 **1W 提高到 3~5W**（1W 在计量噪声下容易误判"有载"→ 永不自动关；
   或误判"无载"→ 误关小功率设备）。

4. **指示灯**：需求要"慢闪呼吸"和"常亮"两态。当前 3 路 LED 无 AC 专用灯，
   建议**复用绿色 LED**（`LED_SIG`）：
   - 输出 AUTO → 1.5s 周期慢闪（现有 `work_led_process` 的 2s 心跳改相位即可）
   - 输出 LATCH → 常亮
   - 无输出 → 回心跳
   若要真正的"呼吸"（渐亮渐暗），需 LED 接 PWM 通道 —— **当前 `Board.h` 的 3 路 LED 都是直连 GPIO**，
   硬件不支持呼吸，只能做"慢闪"。→ 并入 #7（分立电路）一起改。

5. **与 SW-11 的关系**：30min 关输出之后，整机进入空闲 → 再计 1h 关整机（总 90min）。
   若产品意图是"30min 关输出、1h 关整机"并行计时，需明确起点（建议：两计时器独立，均从"最后一次有载"起算）。

**改动**：`app_main_task.c`（`s_state` 新增字段 + 2 个 handler + 重构 `output_idle_check`）、`Board.h`、`work_led_process()`。
**工作量**：2~3 人日。
**风险**：
- **60s → 30min 是行为反转**：现场/售后可能已习惯"拔了负载 1 分钟就自动关"，改后会抱怨"忘记关"。
  必须确认（D3）是**替换**还是**按模式区分**（建议：AUTO=30min、LATCH=不关，正好对应两种用户）。
- 空载判据依赖 `out_ok`；若输出计量芯片掉线，`out_ok=0` 会让计时器停摆 → 需用"最后有效值 + 超时关断"兜底。

### SW-11 1h 低功耗自动关整机（工作簿 #11）

**需求**：如果 1 小时内电源没有给设备供电、也没有给整机充电，会自动关闭整机电源，进入待机。

**现状**：**完全不存在**。`WORK_MODE_SHUTDOWN` 只由 ONOFF 长按进入；
`DEV_POWER_OFF()`（拉低 PB4）只在 `handle_onoff_key()` 调用一次；
`DEV_POWER_ON()` **全工程零调用** → 开机完全由硬件自锁电路完成。

**方案（必须分两步，第二步依赖硬件）**：

**第一步：软件待机（P0，可独立交付）**

```c
/* app_main_task.c 新增 */
#define IDLE_SHUTDOWN_MS  3600000u   /* 1h */
static void idle_shutdown_check(void)
{
    bool idle = (s_state.mode == WORK_MODE_IDLE)          /* 无输出通路 */
             && !s_state.flags.need_charge                 /* 不在充电策略内 */
             && (s_state.charge_state == CHARGE_STATE_IDLE)
             && (ac == AC_INPUT_ABSENT);                   /* 无市电 */
    if (!idle) { s_idle_since = 0; return; }
    if (s_idle_since == 0) { s_idle_since = HAL_GetTick(); return; }
    if (HAL_GetTick() - s_idle_since >= IDLE_SHUTDOWN_MS)
    {
        enter_standby();   /* 见下 */
    }
}
```

`enter_standby()` 的行为分层建议（**按风险从低到高逐步放开**）：

| 级别 | 动作 | 收益 | 风险 |
| --- | --- | --- | --- |
| L1 关屏 | `drv_dwin_set_brightness(0)` | 屏是最大耗电项 | 无 |
| L2 断所有继电器 + 清请求 | `power_abort()` | 消除漏电 | 无 |
| L3 MCU 进 STOP 模式 + IWDG 保持 | `HAL_PWR_EnterSTOPMode()`，按键 EXTI 唤醒 | MCU 电流 mA→µA | 唤醒源需硬件确认 |
| L4 `DEV_POWER_OFF()` | 拉低 PB4 断电 | 最彻底 | **关机后只能靠硬件开机** |

> **强烈建议本轮只做 L1+L2+L3，不做 L4**，理由见风险。

**第二步：真断电（依赖 #14）**

`DEV_POWER_OFF()` 之后 MCU 无电，**软件无法再唤醒**。
若硬件没有"按键直接使能 PWR_EN"的路径，L4 会让设备"变砖"（必须拔电池）。
→ 必须先由硬件确认开机电路（见 #14）。

**改动**：`app_main_task.c`（新函数 + 主循环 1 行）、`drv_dwin`（已有 `set_brightness`，无需改）。
**工作量**：1~2 人日（L1~L3）；L4 待硬件。
**风险**：
- **误关机**：若"无市电 + SOC 低 + 用户拔了负载去吃饭"被判空闲 → 1h 后关机，用户回来无法开机。
  建议加"按键活动刷新计时"（任何按键事件重置 `s_idle_since`）+ SOC 保护（SOC<10% 时才允许 L4）。
- 与 SW-10 叠加后总关断时间 = 30min + 1h = **90min**，需确认是否符合产品预期。

### #14 专项：关机插市电自动开机

**现状**：`DEV_POWER_ON()` 零调用；`DEV_POWER_OFF()` 只拉低 PB4；开机由硬件自锁完成。

| A. 市电检测直接置位 PWR_EN（纯硬件） | 软件上电后读"开机原因"→ 自动进入充电（无需按键）。**推荐** |

### #15 专项：过放/过充激活

**需求**：电池过放（<20V，BMS 已保护）或过充后，插上市电要能激活并充电。

**软件配合点**（需硬件/BMS 先明确）：
1. BMS 保护后通常需要"充电器输出电压"才能唤醒 → 需要 `CHG_IN` 先闭合（**当前时序正是先 CHG_IN 后 CHG_OUT**，方向正确）；
2. 但 `MAX17263` 在电池断开时可能读不到数据 → `battery_protect()` 会判 `BAT_INVALID` 并 `enter_fault()` 锁死 →
   **激活流程会被自己的保护逻辑打死**。需要：
   ```c
   /* 新增 activation 模式: 电池无效 && 有市电 && 无输出 → 允许 charging, 不因 BAT_INVALID 跳闸 */
   ```
3. 建议新增独立状态 `WORK_MODE_ACTIVATE`，超时（如 30s 未恢复通讯）退出并报 `ERR`。

> 这条**当前代码结构上就走不通**（保护逻辑会阻断激活），是 15 条里最容易被低估的一条。

## 六、横切新增设计（4 个）

### 6.1 统一声光告警节奏器（`alarm_rhythm`）

**动机**：需求 #3 要"2.0s 蜂鸣 + 2.0s 闪"，#4 要"1.0s 闪"，image3 定义了 0.5s/1.0s/2.0s 三档，
现有代码是"各处硬编码 `drv_buzzer_short_sound(n)` + 报警灯 500ms 固定闪"，继续打补丁会失控。

**设计**：

```c
typedef enum {
    ALARM_RHYTHM_NONE   = 0,
    ALARM_RHYTHM_URGENT = 500,    /* 过压/欠压: 0.5s 周期 */
    ALARM_RHYTHM_NORMAL = 1000,   /* 过温:     1.0s 周期 */
    ALARM_RHYTHM_SLOW   = 2000,   /* 过载:     2.0s 周期 */
} alarm_rhythm_t;

/* 20ms 调用: 由优先级最高的活跃告警决定节奏, 输出统一相位 */
void alarm_rhythm_process(void);
bool alarm_rhythm_phase(void);   /* true=亮/响 相位, 供 LED/图标/蜂鸣共用 */
```

- **优先级**：FAULT 锁死 > 过载 TRIP > 过载 ALARM > 温度降载 > 通讯 ERR。
- **相位共享**：报警灯、OVERLOAD 图标、蜂鸣器都用同一 `phase`，实现"声光同相"。
- **蜂鸣**：`phase` 上升沿调 `drv_buzzer_long_sound(300)`（现有 API，零调用，正好启用）。
- **图标**：显示任务读 `alarm_rhythm_phase()` 决定写 `ICON_ON`/`ICON_OFF`。

**收益**：把 #3/#4 的闪烁需求收敛成一处，后续加新告警只填一行表。

**成本**：~100 行，1 人日。

### 6.2 输出请求锁存（UPS 化）

见 SW-8。核心是 `power_abort()` 拆分为 `route_all_off()`（断通路）与 `power_abort()`（断通路+清请求），
让"请求"成为独立于"当前通路"的用户意图。

### 6.3 整机电源状态机（PWR FSM）

```
RUN ──(1h 空闲)──► STANDBY(L1+L2+L3) ──(按键/市电)──► RUN
RUN ──(ONOFF 长按2s)──► OFF(断电)  ──(硬件开机)──► RUN
RUN ──(故障)──► FAULT ──(断电重启)──► RUN
```

**要补的缺口**：`fault_active` 无清除路径（`app_main_task.c:444` 只置位）。
建议：过温类故障改为"降载 + 自动恢复（滞回）"，只有通讯硬故障/电池无效才锁死。
否则 #4 的 60℃ 保护会让用户每次都要拔电池。

### 6.4 "无负载"统一判据

目前三处判定不一致 / 缺失：

| 位置 | 判据 | 问题 |
| --- | --- | --- |

## 十二、评审意见与下一步

### 12.1 评审结论

**方案整体可行**，但当前**不具备全量开工条件**：

1. **可立即开工**（P0，6~8 人日）：SW-1、SW-8-L1、SW-11(L1~L3)、6.4 判据统一；
   SW-3/SW-4 的**结构改造**（分级框架 + 节奏器）也可先做，阈值留宏待裁决。
2. **被外部阻塞**：SW-2/SW-5/SW-12 需屏端 DGUS 工程；#6/#7/#9/#13/#14/#15 需硬件方案。
3. **被决策阻塞**：D1（功率口径）与 D5（关机后开机路径）是**最硬的两颗雷** ——
   前者决定 SW-3 能不能写，后者决定 SW-11 会不会把设备变砖。

1. **先开 30 分钟决策会**，只裁决 D1、D2、D5、D9 四项（其余可并行澄清）；

3. **P0 立即排期**，先交付 SW-1（0.5 人日，可当天验证）作为流程打通；
4. **建立"需求 ↔ 代码锚点 ↔ 用例"三向追溯表**（第十一章），后续每次评审只更新此表。
